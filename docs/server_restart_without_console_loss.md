# Перезапуск Сервера Без Остановки Консолей

Статус: реализовано и развёрнуто на `4011` 2026-11-09 после разрешения
пользователя перезапускать рабочий экземпляр. Первоначальное ограничение
«консоли не останавливать» отменено пользователем после их ручной остановки.
Постановка пользователя от 2026-11-09: обновлять/перезапускать сервер
yconhost без остановки уже работающих консольных приложений, с учётом
использования yopenconsole. Текущие рабочие сессии останавливать нельзя.

## Прежние Ограничения

- `src/server/index.ts`: shutdown вызывает `manager.dispose()`.
- `ConsoleManager.dispose()` через `deleteManaged()` убивает каждую сессию.
- `nativeTerminal.ts` запускает worker дочерним процессом HTTP-сервера,
  соединённым Node IPC. Он не имеет переподключаемого интерфейса.
- `nativeTerminalWorker.ts`: обработчик `disconnect` вызывает `kill()`.
  В worker находятся node-pty, ConPTY handles и соединение NativeControl.
- Headless xterm, обработка карточек и запись логов живут на сервере.
  Пока сервера нет, текущая схема не умеет продолжать приём и хранение вывода.
- PM2 на Windows может завершать дерево HTTP-процесса при рестарте.
  Одного удаления явного `kill()` недостаточно и это создаёт утечки процессов.
- Сохранённый PID не позволяет повторно открыть ConPTY stdin/stdout.
  Управляющий pipe yopenconsole умеет show/hide/screen, но не заменяет
  полноценный непрерывный VT-поток с его историей и режимами TUI.

## Реализованная Архитектура

Отдельный постоянный процесс `yconhost-terminal-host` под PM2 владеет
терминалами. Он не должен быть потомком HTTP-сервера. Обновляемый
HTTP/MCP/WebSocket-сервер подключается к нему по локальному именованному
pipe и может отключаться/подключаться, не меняя PID консольных приложений.

Terminal host отвечает за ConPTY workers, чтение вывода при отсутствии
клиентов, ограниченные/ротируемые логи, канонический headless-экран,
input/resize/signal, native show/hide и подтверждённые состояния процессов.
HTTP-сервер отвечает за UI, определения папок и консольных слотов, формы,
авторизацию действий и доставку данных браузеру/MCP. У логов и зеркала
экрана должен быть ровно один владелец, без двух параллельных writers.

Протокол обеспечивает:

- Версию и handshake, локальную ACL/аутентификацию, явные ошибки несовместимости.
- Устойчивый console ID плюс уникальный run ID. PID сам по себе не является
  идентификатором запуска, поскольку Windows может повторно использовать PID.
- Перечисление реально живых запусков и подключение к ним, а не их перезапуск.
- Последовательности output-событий и согласованный
  snapshot с последующими событиями без пропусков и дублирования.
- Полное восстановление terminal state, включая alternate screen, курсор,
  стили, mouse/bracketed-paste/input modes. Одного текстового tail недостаточно.
- Непрерывное draining вывода, ограниченную память, backpressure и ротацию
  во время отсутствия HTTP-сервера. Процесс не должен блокироваться на выводе.
- Идемпотентные запросы управления и подтверждения записи ввода; команды не
  должны повторно исполняться из-за переподключения. Потерянный ответ не
  означает, что ввод не был доставлен.
- Обновление ошибок/карточек с дедубликацией после восстановления связи;
  сохранение read marks и времени ввода/вывода.
- Отдельные операции «остановить сервер» и «остановить все терминалы».
  Close/Delete/Restart конкретной консоли должны остаться явными командами.

Нативный pipe yopenconsole остаётся подключённым к terminal host; HTTP не
конкурирует за единственное native-control соединение. Основной VT-поток
при этом остаётся единственным источником вывода, без оптимистичного echo.
Эта схема также применима к стандартному ConPTY backend.

## Выполненное Внедрение

1. Реализовать terminal-host/protocol и проверять на отдельных портах,
   dataDir, PM2-именах и тестовых консольных приложениях.
2. Подключить к нему ConsoleManager без изменения существующих folder/API
   правил. Восстанавливать соединение с живыми run IDs, а не запускать слоты.
3. Проверить рестарт и принудительное завершение только HTTP-процесса:
   те же PID/run IDs, непрерывный вывод в паузе, прежняя незавершённая строка,
   Tab/Backspace, TUI, браузерный/native ввод, show/hide и карточки без дублей.
4. Проверить пределы replay/логов, недоступный broker, конкурентный ввод,
   повторные запросы, осиротевшие/завершившиеся процессы и очистку после Close.
5. Перейти на схему в согласованное окно обслуживания. Рабочие старые workers
   нельзя прозрачно переподключить новым сервером: у них только старый IPC
   и завершение при disconnect. Первое внедрение может потребовать их
   однократного завершения; сейчас этого не делать.

После внедрения обычный `pm2 restart yconhost` не перезапускает terminal host.
Его собственное обновление или reboot Windows остаются отдельными событиями
и не обещают сохранения процессов. После reboot и при пустом broker нельзя
автоматически запускать сохранённые команды: прежнее правило явного Start
пользователем или агентом остаётся обязательным. Восстановление связи с уже
живым процессом не является автоматическим запуском новой консоли.

## Операции

```powershell
pnpm build
pm2 start ecosystem.config.cjs
pm2 save
# Повседневный перезапуск HTTP/MCP без потери сессий:
pm2 restart yconhost
```

В PM2 теперь две разные роли: `yconhost` и `yconhost-terminal-host`, это не
дубли сервера. Второй процесс является родителем ConPTY и native workers.
Не выполнять `pm2 restart all` для обновления только UI/API. Если изменён
сам terminal host или его протокол, его перезапуск требует отдельного окна
обслуживания. Старые сессии, запущенные до миграции, нельзя присоединить.

`pnpm start` и `dev:server` используют broker по умолчанию. Он не запускается
дочерним процессом HTTP; его нужно отдельно запустить через PM2 с тем же
абсолютным settings path и dataDir. Для внутренних legacy/fake тестов есть
`YCONHOST_TERMINAL_MODE=direct`; этот режим не сохраняет процессы при рестарте.
Нет скрытого fallback из broker в direct. `/api/health` возвращает 503 при
потере host, даже если сам HTTP-процесс работает.

Адрес pipe выводится из абсолютного dataDir. Файл `terminal-host-token.json`
содержит случайный 256-bit ключ; не публиковать его. Применяются локальные
ACL Windows и дополнительная проверка ключа/версии. Максимум 1024 живых
запуска, frame 16 MiB, backlog соединения 4 MiB; медленный клиент отключается
и получает новый канонический snapshot после reconnect. `list` разбит на
страницы по 16 запусков. Ввод ограничен 1 MiB на запрос.

Дедупликация изменяющих RPC действует по request UUID, содержимому и сроку
60 секунд, до 16384 записей. Неистёкшие запросы не вытесняются для повторного
исполнения; при заполнении новый запрос отклоняется. Просроченный запрос
отклоняется даже после удаления кеша. При потере подтверждения ввод
автоматически **не повторяется**: клиент получает ошибку неопределённой
доставки. В браузере stdin выключен до получения нового snapshot.

Headless xterm 5.5 и совместимый официальный `@xterm/addon-serialize` 0.13
сериализуют оба буфера, стили, курсор и modes. Источник совместимости:
[xterm 5.5 releases](https://github.com/xtermjs/xterm.js/releases/tag/5.5.0).
Начальная загрузка и reconnect используют один WS-протокол snapshot + события
с sequence; прежняя гонка HTTP replay и WS подписки удалена. Логи пишет только
terminal host; перед доставкой события файл доступен серверу для карточек.

Изменения log/temporaryConsoles из Preferences и при reconnect передаются
владельцу через `configure`: ротация и TTL не требуют его перезапуска.
Пределы: log-файл 1 KiB..1 GiB, 1..32 файла ротации, tail 1 KiB..64 MiB,
TTL 0..8760 часов (0 отключает очистку), период очистки 1 секунда..1 сутки.
Ошибочные значения отклоняются до записи settings.json5. Об истечении TTL
host сообщает отдельно: временный слот удаляется, а не остаётся остановленным
ещё на один TTL из-за финальной строки выхода в логе.

### Границы Гарантии

Работающие команды продолжаются при остановке HTTP. Сам HTTP/MCP-запрос
`run_console_command`, ожидающий ответ в момент рестарта сервера, обрывается
вместе с HTTP-соединением; результат можно прочесть через состояние/лог после
reconnect. Promise и HTTP-ответ не переносятся между процессами, команда
повторно не отправляется. Отдельный устойчивый job API здесь не добавлялся.

Не гарантируется сохранение сессий после обновления terminal host, его
падения, выключения Windows или отключения питания. После такого события
восстанавливаются только idle slots, без автоматического исполнения команд.
