# Открытые вопросы по эталонному ТЗ yconhost


Статус: ответы получены 2026-05-19, реализация начата в текущей папке.

## Принятые решения

- `@xterm/headless` и карточки сообщений являются core feature.
- От `node-pty` нужно отказаться. Runtime переписывается в текущей папке; старое состояние зафиксировано tag `last-node-pty`.
- Behavioral reference создан в `D:\b\Mine\GIT_Work\yconhost_old_node_pty`.
- Новая ветка не создается.
- Визуальную часть можно переиспользовать, но старый backend/runtime/tracker код должен уйти.
- Поведение первой версии должно сохранить существующий смысл функций, кроме измененного server-client flow и карточек.
- Основное хранение карточек - текстовые логи консоли. Карточки извлекаются из логов при загрузке/обновлении; кеш допустим, но не является source of truth.
- Логи по умолчанию ограничены 10 MB на файл и 3 файлами ротации, то есть около 30 MB на консоль. Значения настраиваются.
- Unread counters полностью переходят на extracted cards.
- Точный click-to-scroll к карточке в первой версии не нужен.
- Backend terminal size по умолчанию `120x40`; значение выносится в `settings.json5` и Preferences UI.
- Формат `mywins.json` / `my_wins.json` остается существующим; ошибки парсинга показываются пользователю.
- HTTP API можно менять, обратная совместимость текущего API не обязательна.
- Лимиты данных задаются разумными defaults и выносятся в `settings.json5` и Preferences UI.
- Acceptance проверяется на `D:\b\Mine\GIT_Work\books_lib`; этот проект нельзя изменять.
- UX карточек можно реализовывать по шагам, но к просмотру нужен проверенный backend и frontend перенос.

Ниже сохранен исходный список вопросов как checklist.

## 1. Rewrite или постепенная доработка

Нужно решить, является ли `@xterm/headless` и карточки сообщений core feature.

- Если да, переписывать архитектуру вокруг `node-pty` + backend headless xterm с первого дня.
- Если нет, продолжать текущий прототип небольшими доработками и оставить карточки как отложенную архитектуру.

## 2. Где вести новую реализацию

Нужно выбрать формат работы:

- новая ветка в текущем репозитории;
- новая чистая директория/репозиторий;
- продолжение текущего кода с крупным refactor.

Для rewrite предпочтительнее новая ветка или чистая директория, чтобы текущий проект остался behavioral reference.

## 3. Что считать утвержденным scope первой версии

Нужно явно зафиксировать минимальный набор возможностей первой версии:

- консоли и lifecycle;
- проекты из `mywins.json` / `my_wins.json`;
- recent projects;
- persistence;
- HTTP API и MCP;
- карточки ошибок/сообщений;
- debug mode или его замена.

Без этого rewrite легко расползется в перенос всех идей сразу.

## 4. Хранить ли extracted cards между рестартами

Нужно решить, persistent cards живут только в памяти процесса yconhost или сохраняются на диск.

Варианты:

- не сохранять карточки, потому что raw logs уже являются source of truth;
- сохранять карточки отдельно для быстрого UI и unread state;
- восстанавливать карточки из логов при старте.

## 5. Как должны работать unread counters

Нужно определить источник счетчиков:

- оставить текущий raw tracker для unread errors;
- полностью перейти на extracted cards;
- временно поддерживать оба механизма во время миграции.

Также нужно решить, считаются ли unread только `error`, или также `warning` / `message`.

## 6. Какой статус должен иметь debug mode

Нужно решить, сохранять ли текущий debug mode как отдельную диагностическую панель.

Варианты:

- заменить его панелью карточек;
- оставить debug mode только для разработки extractor;
- удалить после перехода на headless xterm.

## 7. Как выбирать canonical terminal size

Backend mirror требует размера терминала. Нужно выбрать правило, если одну консоль смотрят несколько браузерных клиентов с разными размерами.

Текущий кандидат: last active client size, fallback `120x40`.

Нужно подтвердить, достаточно ли этого, или нужен более строгий механизм ownership/active viewer.

## 8. Нужен ли точный click-to-scroll к карточке

Backend `bufferY` будет приблизительным из-за отличий wrapping между backend mirror и browser xterm.

Нужно решить:

- не делать click-to-scroll в первой версии;
- делать приблизительный переход;
- строить точный механизм через client-side markers/decorations;
- рассмотреть `@xterm/addon-serialize` позже.

## 9. Как идентифицировать проект

Нужно окончательно закрепить project identity:

- normalized absolute `projectPath` как основной ключ;
- basename проекта только как display name;
- fallback по старому `project` name только для миграции.

Также нужно решить, как обрабатывать переезд папки проекта.

## 10. Какой формат `mywins.json` считать поддерживаемым

Нужно зафиксировать точную схему поддерживаемого project config:

- обязательность `wins`;
- поля `cmd` и `command`;
- поведение `cwd`;
- поддержка `no_run`;
- допустимые дополнительные поля;
- поведение при ошибках парсинга.

## 11. Что делать с неработающими сохраненными консолями после рестарта

После рестарта yconhost пересоздает console definitions, но не re-attach'ится к старым процессам.

Нужно решить:

- автозапускать все сохраненные консоли;
- восстанавливать их как stopped/exited до ручного старта;
- различать обычные консоли и проектные консоли.

## 12. Какой уровень API совместимости нужен

Нужно решить, является ли текущий HTTP API контрактом, который нельзя ломать, или новый rewrite может менять API.

Отдельно нужно зафиксировать минимальный MCP surface:

- list consoles;
- read console output;
- write console input;
- нужны ли project actions через MCP.

## 13. Как ограничивать размер данных

Нужно определить конкретные defaults и лимиты:

- max log size;
- rotated log files count;
- in-memory scrollback;
- headless mirror scrollback;
- максимальное количество карточек на консоль;
- retention для старых карточек.

## 14. Как тестировать acceptance scenario

Нужно решить, делать ли `D:\b\Mine\GIT_Work\books_lib` обязательным локальным acceptance fixture.

Если да, тесты должны не изменять этот проект. Если нет, нужен синтетический fixture внутри текущего репозитория.

## 15. Какой UX считать обязательным для первой версии карточек

Нужно зафиксировать минимум UI:

- панель карточек над xterm или рядом с ним;
- фильтры по категориям;
- collapse/expand;
- mark read;
- отображение counts;
- отсутствие overlay поверх терминала.

Все более сложное, включая точный переход к строке терминала, лучше вынести во вторую фазу.
