# Универсальные папки консолей

Дата: 2026-10-31.
Статус: черновик для согласования. Разрешения на реализацию нет.

Документ отделяет требования пользователя от предложений и открытых вопросов.
Ответы на вопросы нужно заносить сюда; после ответов согласовывается итоговая
редакция. До этого не менять приложение, настройки сервиса или исходный Markdown.

## 1. Исходная постановка

Пользователь хочет обобщить существующую папку `codexes`: интерактивно собираемые
папки должны задаваться отдельными серверными JS-файлами, а не специальной логикой
ядра только для Codex. Убрать `Import Codex contexts` из общего верхнего меню.
Добавить каждой папке пункт `Settings` в её собственном меню и диалог настроек
с типом папки:

- `manual`: пример — `Default`; пользователь сам создаёт и удаляет консоли.
- `my_wins`: состав и настройки берутся из файла проекта.
- `scripted`: пример — `codexes`; JS читает Markdown и возвращает определения
  элементов, достаточные для формирования папки.

У скрипта могут быть дополнительные функции: `createFields` возвращает описание
полей формы создания, пока только типа `string`; `create`, `delete`,
`update`/переименование меняют собственный источник скрипта. Например, добавляют
раздел Markdown, помечают его отключённым или переименовывают заголовок.

Уточнение пользователя: идентификатор элемента — например, GUID сессии.

## 2. Требования из сообщения пользователя

R01. Папка имеет явный тип, а тип определяет источник состава и способы изменения.

R02. `codexes` становится экземпляром универсальной scripted-папки. В ядре и UI
не должно быть отдельной бизнес-логики импорта именно для этого имени папки.

R03. Скрипт работает на сервере и находится в отдельном JS-файле. Браузер не читает
Markdown и не исполняет этот JS.

R04. Результат чтения скрипта — массив определений консолей, содержащий входные
данные для формирования папки. Точная схема результата ещё согласовывается.

R05. Каждая папка имеет собственный пункт `Settings` и диалог настроек. Тип папки
отображается в диалоге. Возможность смены уже установленного типа пока не решена.

R06. Специальное действие `Import Codex contexts` исчезает из верхнего бургера.
Действия, относящиеся к источнику конкретной папки, находятся в её меню.

R07. Если скрипт реализует операции изменения элементов, приложение вызывает эти
обработчики; модификацию исходного файла реализует скрипт, а не ядро yconhost.

R08. `createFields` описывает поля диалога создания. В первой версии поддерживается
только тип поля `string`; точные атрибуты поля ещё не утверждены.

R09. Элемент должен иметь устойчивый идентификатор, например GUID сессии.
Отображаемое имя не является идентификатором. Переименование не создаёт новую
консоль, а перезапуск процесса сам по себе не меняет идентификатор элемента.

R10. Реализацию начинать только после полноценного согласования требований.

## 3. Что есть сейчас

По состоянию репозитория на момент подготовки документа:

- `src/server/codexContexts.ts` читает Markdown и встроенные Lua-пресеты WezTerm,
  поддерживает Codex/ycodex и Claude, сохраняет команды, каталоги и цвета.
- `ConsoleManager` отдельно вызывает импорт Codex при старте и предоставляет
  отдельный метод импорта. Повторный импорт сопоставляет элементы по проекту/имени.
- Идентификатор новой импортированной консоли сейчас вычисляется из имени проекта
  и имени элемента. GUID агента из команды отдельно ключом источника не хранится.
- Сам парсер также удаляет дубли по совпадающей строке команды. Это поведение
  конкретного источника, его не следует автоматически навязывать другим скриптам.
- `Gather errors` по умолчанию выключается проверкой имени `codexes` или имени
  проекта из глобальных `codexContexts` настроек. Это тоже часть обобщения.
- Глобальные настройки содержат отдельный блок `codexContexts`; UI и HTTP/MCP
  имеют отдельные действия импорта.
- Для `mywins.json`/`my_wins.json` уже есть чтение, добавление, редактирование,
  удаление и перезагрузка. Внутреннее имя нового типа предлагается писать
  `my_wins`; это не отменяет поддержку обоих существующих имён файлов.
- Для файловых проектов удаление уже требует подтверждения в UI и меняет файл.
  Обычный Close сохраняет слот. В Default Close удаляет регистрацию целиком.
- Обычное переименование заголовка сейчас меняет запись yconhost, а отдельная
  форма mywins умеет менять источник. Нельзя оставить два разных пути rename,
  один из которых обходит новый обработчик источника.
- Есть MCP/UI-managed проекты без файла и отдельная read-only группа `pm2`.
  Обобщение не должно случайно потерять эти сценарии.
- `ProjectStore` сохраняет метаданные папок в `managed-projects.json`, а
  `ConsoleStore` — определения консолей в `consoles.json`. Не все текущие папки
  представлены самостоятельной полной записью: часть выводится из списка консолей.

## 4. Предлагаемая модель, пока не утверждена

### 4.1. Папка и её источник

Папка имеет собственный устойчивый ID, отображаемое имя, тип, конфигурацию
источника и общие настройки. Имя не используется как ключ поведения.

Для `manual` определения хранятся в состоянии yconhost. Для `my_wins` источником
служит файл проекта. Для `scripted` конфигурация содержит путь к JS-модулю и его
параметры: например, путь к Markdown и необязательным Lua-пресетам.

Предложение: расширить существующий реестр проектов, а не заводить параллельный
второй механизм папок. В Settings показывать общие параметры и параметры источника.
`Gather errors`, правила Close и другие особенности мигрировать в явные настройки
папки, а не сохранять проверки строк `Default`/`codexes` в ядре.

### 4.2. Предлагаемый контракт JS-модуля

Имена, сигнатуры и формат ниже — эскиз контракта, не готовая спецификация API.

| Экспорт | Назначение | Обязательность, предложение |
| --- | --- | --- |
| `list(context)` | Прочитать источник и вернуть полный упорядоченный список | Обязателен |
| `createFields(context)` | Описать строковые поля создания элемента | Необязателен |
| `create(context, values)` | Создать элемент в источнике | Необязателен |
| `update(context, itemId, patch)` | Изменить элемент, в том числе имя | Необязателен |
| `delete(context, itemId)` | Удалить или отключить элемент в источнике | Необязателен |

Предлагается поддержать асинхронные функции. `context` содержит ID папки,
конфигурацию и необходимые служебные данные, но не предоставляет способ обходить
менеджер процессов или самостоятельно регистрировать консоли в обход общего sync.
Сам JS при этом остаётся доверенным серверным кодом, а не безопасной песочницей.

Определение элемента содержит устойчивый ID, имя, команду, cwd и необходимые
опции запуска/отображения: shell/args, цвет, no_run и согласованные defaults.
Runtime-поля PID, статус процесса, время последнего вывода и прочие данные сессии
не должны приниматься от источника как актуальное состояние процесса.

Предложение по полю формы: `name`, `label`, `type: "string"`, необязательные
`required` и `defaultValue`. Описание полей не является HTML/JS для браузера;
сервер валидирует значения и вызывает обработчик с обычными строками.

После успешной мутации источник перечитывается через `list`, а общий механизм
применяет результат. UI и MCP должны использовать один путь операций, включая
переименование из заголовка консоли. Отдельно уточнить поведение при наличии
обработчика без описания формы и форму редактирования.

### 4.3. Идентичность

Уточнение про GUID принято как основа. ID элемента должен оставаться тем же при
повторном чтении и rename. Произвольно генерировать новый GUID на каждом `list`
нельзя: это снова создаст дубли и потеряет связь с историей.

Предлагается разделить ключ элемента источника и существующий runtime ID yconhost,
сохраняя связь между ними при миграции. Если GUID уже есть в команде resume,
скрипт может использовать его. Для элементов без GUID место хранения нового ID
нужно согласовать отдельно. Ключ принадлежности — папка плюс ID элемента: один
источник может использоваться несколькими папками без случайного слияния слотов.

Совпадение имён или команд само по себе не означает, что это один элемент.
Правила распознавания секций, отключения и устранения дублей относятся к скрипту
конкретного источника. Повтор одного ID внутри одной выдачи должен считаться ошибкой.

### 4.4. Обновление и работающие процессы

Предлагаемые правила сохранения текущего поведения:

- Загрузка/обновление scripted-папки создаёт недостающие idle-слоты, но не запускает
  команды. Сохраняется запрет автозапуска консолей при старте сервиса.
- Порядок в папке определяется результатом источника. Успешный повторный sync
  идемпотентен и не создаёт дополнительные процессы или регистрации.
- Изменение имени сохраняет runtime ID, историю, отметки прочтения и PID.
- Изменение команды/cwd не перезапускает работающий процесс. Новое определение
  применяется при следующем явном Start/Restart; разницу нужно показать в UI.
- Ошибка чтения не равна пустому списку. При ошибке сохраняются последний успешный
  состав и работающие сессии, а папка получает видимое сообщение об ошибке.
- Исчезновение элемента при внешнем редактировании и явное Delete — разные случаи.
  Для них требуется согласовать отдельные правила, см. Q06–Q08.
- Скрипт отвечает за безопасную запись своего источника, сохранение посторонних
  разделов/разметки и обнаружение конфликтов внешнего редактирования. При ошибке
  записи нельзя сначала удалить локальный слот или остановить процесс.
- Случай «источник записан, но последующий list завершился ошибкой» показывается
  явно; не обещать общей транзакции/автоматического отката произвольного JS.

### 4.5. UI и возможности

- Общий верхний бургер не содержит Codex-специфичного импорта. Общая команда
  создания папки, если согласована, остаётся общей, без привязки к Codex.
- В меню каждой папки есть `Settings`; для источников есть общий `Refresh`.
- Тип и конфигурация источника видны в Settings. Окончательный набор полей — Q02.
- Доступные Create/Edit/Rename/Delete определяются возможностями источника,
  а не именем папки или наличием projectPath в UI.
- Отсутствующий обработчик изменения не подменяется локальной мутацией, которая
  пропадёт при следующем обновлении. UI и MCP должны давать согласованный ответ.
- Удаление записи источника требует подтверждения. Close/Stop процесса не должны
  незаметно вызывать удаление секции Markdown или записи mywins.
- Поиск, компактное/полное отображение, Touch mode, цвета и карточки сохраняются.

## 5. Вопросы для согласования

### Q01. Экземпляры папок и регистрация

Может ли один JS обслуживать несколько папок с разными параметрами, например
разными Markdown-файлами? Создаём и настраиваем такие папки через UI и MCP?

Предложение: да; папка — запись реестра с `scriptPath` и параметрами, JS —
переиспользуемый модуль. Не считать имя JS-файла идентичностью папки.

### Q02. Settings и смена типа

Нужны ли описания полей Settings от самого скрипта, отдельно от `createFields`
для создания консоли? Можно ли менять тип уже существующей папки?

Предложение: общие поля и строковые параметры источника в Settings; при
необходимости согласовать необязательный `settingsFields`. В первой версии тип
показывать, но не менять у непустой папки без отдельной процедуры преобразования.

### Q03. Когда перечитывать источник

Достаточно загрузки при старте сервиса, кнопки Refresh и перечитывания после
create/update/delete, либо сразу нужен watch за Markdown/JS или периодический sync?

Предложение: старт + Refresh + успешные мутации; без watch в первой версии.
При Refresh перечитывать и JS-модуль, чтобы его правки не требовали рестарта сервиса.

### Q04. Необязательные обработчики и поля

Если нет create/update/delete, соответствующую операцию скрывать/запрещать?
Если create есть, а createFields нет, нужна стандартная форма или создание без формы?

Предложение: нет обработчика — нет операции; нет createFields — стандартная форма
имя/команда/cwd. Один createFields без create не включает создание.

### Q05. Объём update

В первой версии update нужен только для rename или также для команды, cwd, цвета
и других параметров элемента? Подходит ли та же схема полей для создания и редактирования?

Предложение: update меняет согласованные поля источника; rename — частный случай
update. Не вводить параллельный локальный rename, не записывающий изменения в источник.

### Q06. Явное удаление и Close

Для codexes Delete физически удаляет раздел или ставит отметку disabled?
Подтверждённое удаление работающей консоли должно также остановить её процесс?

Предложение: для Markdown мягкое отключение, для mywins сохранение текущего
удаления записи; решение об источнике реализует адаптер. Остановить процесс после
успешной записи и подтверждения. Существующие различия Close у Default и файловых
папок сохранить явной политикой папки, а не проверкой её имени.

### Q07. Элемент исчез из источника извне

При Refresh автоматически убирать отсутствующие элементы? Что делать с работающей
консолью, если её раздел удалён/отключён внешним редактором?

Предложение: idle-слот убрать из актуального состава, логи не стирать; работающую
сессию не убивать, а показать как потерявшую связь с источником до явного решения.

### Q08. Изменение работающей консоли

Подходит ли правило: rename/метаданные обновляются без перезапуска, а команда/cwd
меняются только для следующего Start/Restart, с обозначением этого в UI?

Предложение: да; Refresh и сохранение настроек сами процессы не перезапускают.

### Q09. Откуда брать ID, если GUID пока нет

GUID сессии как пример устойчивого ID уже уточнён пользователем. Но для нового
раздела с командой без resume GUID сессии может ещё не существовать. Разрешается ли
скрипту записать отдельный UUID в Markdown, например невидимым HTML-комментарием?

Предложение: да; генерировать единожды при создании/миграции, затем читать из
источника. Альтернатива — отдельная таблица соответствий, но внешние rename
без явного ID будут менее надёжны. Сам Markdown до согласования не менять.

### Q10. Доверие к JS и защита от зависания

Это доверенные локальные Node.js-скрипты с доступом к файловой системе сервера?
Нужен ли доступ к сторонним пакетам/запуску других программ?

Предложение: первая версия для доверенных локальных модулей, без загрузки кода
из браузера или URL. Выполнение отделить от основного серверного потока с
ограничением времени, чтобы зависший скрипт не блокировал UI/терминалы. Такая
изоляция выполнения не является защитной песочницей для недоверенного JS.

### Q11. HTTP/MCP и совместимость

Нужны ли все операции папок/элементов одинаково через UI, HTTP и MCP?
Можно ли сразу удалить старый import_codex_contexts API/MCP, или оставить alias?

Предложение: общий контракт для всех клиентов; старое имя временно оставить
тонким совместимым вызовом Refresh мигрированной папки, без старого импортёра.
Убрать legacy alias можно отдельным согласованным изменением.

### Q12. PM2

Оставляем pm2 системной read-only папкой вне трёх пользовательских типов первой
версии, с доступным просмотром Settings, но без редактирования источника/процессов?

Предложение: да; не расширять сейчас контракт скриптов чтением live-вывода
чужих процессов. Настройки readonly-папки не должны включать мутации PM2.

## 6. План после согласования

1. Утвердить ответы Q01–Q12, модель ID, контракт модуля и формы; обновить статус
   этого документа. Это отдельная точка разрешения реализации.
2. Ввести явные определения папок и общий механизм источников, переиспользуя
   текущий ProjectStore и адаптируя существующие manual/mywins пути.
3. Перенести чтение codexes в отдельный JS-модуль: Markdown/Lua, правила Codex/Claude,
   цвета, порядок, defaults. Ядро работает только с общим контрактом.
4. Мигрировать существующие папки и сопоставления ID без потери логов, настроек
   Gather errors, отметок прочтения и времени запусков. Миграция не запускает
   процессы и не переписывает внешние источники без согласованной необходимости.
5. Добавить Settings папок, общий Refresh и capability-based формы/действия;
   убрать верхний Codex-импорт. Подключить тот же путь к HTTP/MCP и header rename.
6. Проверить сначала на копиях Markdown/mywins и отдельном экземпляре сервера;
   согласовать применение к живому сервису и исходным файлам.

## 7. Предлагаемые критерии приёмки

- Две scripted-папки с разными JS или разными параметрами одного JS работают
  независимо, без специальных проверок имён в ядре/UI.
- Default/manual и оба имени файлов mywins сохраняют согласованное поведение.
- Нет верхнего пункта Import Codex contexts; у каждой папки доступны её Settings.
- Функции create/update/delete вызываются только при соответствующей возможности;
  отмена формы/подтверждения не вызывает мутацию источника.
- Операции меняют источник, и результат сохраняется после Refresh/перезапуска.
- Rename не меняет идентичность элемента и не теряет историю; новые/исчезнувшие
  GUID и повторные ID обрабатываются по согласованным правилам.
- Ошибка или зависание JS не очищает папку и не останавливает её процессы.
- Конфликт внешней записи не затирает чужие изменения. Изменяется только нужный
  раздел; нет массового переформатирования Markdown или разрушения иных данных.
- Повторный Refresh не создаёт дублей и процессов. Старт сервиса остаётся без
  автозапуска консолей. Изменения running-сессий и удаление проверены отдельно.
- UI, HTTP и MCP не обходят правила источника, в том числе при обычном rename.
- Проверки охватывают readonly-источник, отсутствующие/ошибочные обработчики,
  файловые ошибки, пустой успешный список и отказ чтения как разные ситуации.
