# Универсальные папки консолей

Дата: 2026-10-31.
Статус: требования уточнены ответами Q01–Q12; остаются последние уточнения
и согласование итоговой редакции. Разрешения на реализацию пока нет.

Документ отделяет решения пользователя от технических предложений. До полного
согласования не менять приложение, настройки сервиса или исходный Markdown.

## 1. Исходная постановка

Обобщить существующую папку `codexes`: интерактивно собираемые папки задаются
отдельными серверными JS-файлами, а не специальной логикой ядра только для Codex.
Убрать `Import Codex contexts` из общего верхнего меню. Добавить каждой папке
пункт `Settings` в её собственном меню и диалог настроек с типом папки:

- `manual`: пример — `Default`; пользователь сам создаёт и удаляет консоли.
- `my_wins`: состав и настройки берутся из файла проекта.
- `scripted`: пример — `codexes`; JS читает Markdown и возвращает определения
  элементов, достаточные для формирования папки.

Скрипт может описывать поля создания и редактирования, пока только типа `string`,
и реализовывать `create`, `update`, `delete`. Именно скрипт меняет свой источник:
например, добавляет раздел Markdown, помечает отключённым или переименовывает.
Первоначальное имя `createFields` заменено пользователем на `defineFields`.

Идентификатор элемента источника — например, GUID сессии. Пользователь дополнительно
уточнил, что `session_id` можно менять; при отсутствии GUID сопоставление по имени.

## 2. Ответы Q01–Q12

### Q01. Соотношение папки и JS

Ответ: «нет, одна папка — один js».

У каждой scripted-папки собственный JS-файл. Не проектировать несколько
параметризованных экземпляров папок поверх одного общего скрипта как требование.
Общие библиотечные функции не означают второй механизм регистрации папок.
Ответ не определяет отдельно способ регистрации новой scripted-папки;
универсальная регистрация через UI/HTTP/MCP остаётся техническим предложением.

### Q02. Настройки от скрипта и смена типа

Ответ: «нет».

Исходный вопрос содержал две части: отдельную схему полей Settings от скрипта
и возможность менять тип существующей папки. Предварительное прочтение: обе
возможности не нужны. Подтверждение этой трактовки — F01 ниже. Общий диалог
Settings, в том числе частота обновления, остаётся обязательным.

### Q03. Обновление источника

Частота вызова скрипта должна быть настройкой папки. У скрипта несколько
функций-точек входа, в частности `refresh`. Ранее предложенного режима только
«старт + ручное обновление + мутации» недостаточно: нужен периодический вызов.

### Q04. Необязательные операции и форма

Нет обработчика — нет соответствующей операции. Если `defineFields` отсутствует,
стандартная форма содержит ровно два поля: `name` и `description`.
Наличие `defineFields` само по себе не включает отсутствующую операцию.

### Q05. Редактирование и ошибки

Создание и изменение используют один диалог и одну схему `defineFields`.
Пользователь может изменять любые поля этой схемы; значения передаются в `update`.
Правила изменения реализует скрипт, а не ядро.

Для скрипта Codex:

- Изменено только имя: найти раздел по исходному `session_id`, изменить имя.
- Изменён только `session_id`: найти раздел по исходному имени, изменить ID.
- Изменены одновременно имя и `session_id`: обработчик делает `throw`.
- Ошибка отображается внизу диалога; значения возвращаются к исходным,
  диалог остаётся открытым для новой попытки.

Это правило относится к скрипту Codex, а не ко всем scripted-папкам.

### Q06. Удаление

Удаление в Markdown обратимое: добавить `DELETED` в начало заголовка H1.
Например, `# example` становится `# DELETED example`. Удаление маркера вручную
восстанавливает доступность раздела при следующем обновлении.

Ответ «да» принят в контексте предложения мягкого удаления и остановки работающей
консоли после подтверждения и успешной записи источника. Не удалять секцию целиком.
Для mywins сохраняется удаление записи файла; Close/Stop не равны Delete.

### Q07. Исчезновение элемента извне

Ответ: «по идее да, но помечаем orphaned».

Прочтение в контексте исходного вопроса: отсутствующий idle-слот убирается из
актуального состава без удаления логов; работающая сессия сохраняется, не
останавливается автоматически и получает отметку `orphaned` — связь с источником
потеряна. Это не то же действие, что подтверждённое пользователем Delete.

### Q08. Изменение работающей консоли

Да: имя и метаданные обновляются без перезапуска. Новые команда/cwd применяются
при следующем явном Start/Restart; отличие от работающей конфигурации видно в UI.

### Q09. Элемент без GUID

Ответ: «сопоставляем по имени тогда».

Не добавлять автоматически UUID или скрытые комментарии в Markdown.
Для элемента без `session_id` ключом сопоставления служит имя внутри папки.

### Q10. Доверие к скрипту

Да: доверенный серверный Node.js-код; сервер — личный компьютер пользователя.
Доступ к локальной файловой системе и другим программам допустим. Это не
песочница для недоверенного кода.

### Q11. UI, HTTP, MCP и старый импорт

Общие операции нужны через UI, HTTP и MCP. Старый Codex-специфичный импорт
не оставлять, в том числе как совместимый alias. Вместо него общий `refresh`.

### Q12. PM2

Перевести PM2 в `scripted`, а не оставлять исключением в ядре. Как сохранить
нынешний read-only сценарий в общем контракте — предложение и уточнение F03 ниже.

## 3. Проверенное текущее состояние

На момент подготовки документа:

- `src/server/codexContexts.ts` читает Markdown и встроенные Lua-пресеты WezTerm,
  поддерживает Codex/ycodex и Claude, команды, каталоги и цвета. Маркер `DELETED`
  пока не обрабатывает. Парсер устраняет дубли по строке команды.
- `ConsoleManager` отдельно импортирует Codex при старте и по специальному вызову.
  Повторный импорт сопоставляет элементы по проекту/имени. Новый ID консоли
  вычисляется из этих имён; GUID агента отдельно как ключ источника не хранится.
- Выключение `Gather errors` для Codex завязано на имя папки и глобальные
  `codexContexts` настройки; UI и HTTP/MCP имеют отдельный импорт.
- `mywins.json` и `my_wins.json` уже поддерживают чтение и CRUD/перезагрузку.
  Внутреннее имя типа `my_wins` не отменяет поддержку обоих имён файлов.
- В файловых проектах Delete требует подтверждения и меняет файл; Close сохраняет
  слот. В Default Close удаляет регистрацию. Обычное переименование заголовка
  сейчас меняет локальную запись; нельзя оставить обход нового `update`.
- Есть manual-проекты, управляемые через MCP/UI. Временные консоли по умолчанию
  и их TTL должны сохраниться; это не основание делать импортированные слоты temp.
- `ProjectStore` сохраняет метаданные в `managed-projects.json`, `ConsoleStore` —
  определения в `consoles.json`. Часть папок сейчас выводится из списка консолей.
- `src/server/pm2Monitor.ts` отдельно вызывает `pm2 jlist` и читает stdout/stderr
  из файлов PM2. Он показывает статус/PID и readonly-вывод чужих процессов,
  но не создаёт их, не отправляет ввод и не управляет их запуском/остановкой.
  HTTP API отдельно распознаёт проект `pm2` и префикс ID `pm2:`.

## 4. Модель и контракт для итогового согласования

Ниже техническое развитие принятых решений. Неоговорённые детали остаются
предложениями до согласования итогового документа.

### 4.1. Папки и настройки

Расширить текущий реестр проектов, не создавать параллельный реестр папок.
Папка имеет внутренний устойчивый ID, имя, тип, настройки и конфигурацию источника.
Имя папки не определяет поведение ядра.

- `manual`: определения хранятся в yconhost.
- `my_wins`: источник — файл проекта.
- `scripted`: источник задаётся собственным серверным JS-файлом папки.

Settings содержит общие настройки, для scripted — путь к JS и период обновления.
Скриптовую схему Settings не вводить, если подтверждено прочтение Q02. Настройки
источника Codex (пути Markdown/Lua) могут находиться в его JS; не путать их
с `defineFields`, описывающей элементы, а не саму папку.

`Gather errors`, правила Close и другие различия перенести в явные свойства
папки/источника. Сохранить текущие значения, а не сбрасывать при миграции.

### 4.2. Точки входа JS

Предлагаемый эскиз сигнатур; имена `refresh` и `defineFields` отражают ответы:

| Экспорт | Назначение | Обязательность |
| --- | --- | --- |
| `refresh(context)` | Вернуть полный упорядоченный состав папки | Обязателен |
| `defineFields(context)` | Описать общие поля создания/изменения | Необязателен |
| `create(context, values)` | Создать запись в источнике | Необязателен |
| `update(context, original, values)` | Изменить исходную запись | Необязателен |
| `delete(context, original)` | Удалить/отключить исходную запись | Необязателен |

Поддержать асинхронные функции. `original` содержит исходные ключи и значения,
чтобы изменение `session_id` или имени не мешало найти прежний раздел. Новые
значения приходят отдельно. Скрипт отвечает за свою бизнес-валидацию и запись.
После успешной мутации выполнить `refresh` и применить его результат общим путём.

Поля: `name`, `label`, `type: "string"`, необязательные `required` и `defaultValue`.
Это предложение атрибутов схемы, не HTML/JS для браузера. Сервер проверяет типы;
специфические ограничения источника проверяет обработчик. Без `defineFields`
форма имеет только `name` и `description`, как согласовано в Q04.

Определение управляемой консоли включает ключи источника, имя/описание, команду,
cwd и опции запуска/отображения: shell/args, цвет, no_run и defaults. Живое
состояние собственного процесса вычисляет yconhost, а не скрипт.

### 4.3. Идентичность и обновление Codex

Различать внутренний ID консоли yconhost и редактируемый ключ источника
`session_id`. Изменение ключа через успешный `update` не создаёт новую консоль
и не теряет её историю, отметки прочтения или работающий процесс.

При повторном чтении сопоставлять по `session_id`, если он есть, иначе по имени
внутри папки. Никаких новых UUID в Markdown. При редактировании использовать
исходные значения; для Codex действуют ограничения Q05. Имя и `session_id`
не могут одновременно измениться в одной операции этого скрипта.

Предложение для неоднозначностей: дубли ключей и неоднозначные имена выдавать
как ошибку, а не выбирать произвольный раздел. Если внешним редактором одновременно
изменены все доступные ключи, не угадывать соответствие: это исчезнувший старый
элемент и новый элемент. Сохранение истории при таком внешнем изменении не обещается.

### 4.4. Обновление и работающие процессы

- Период обновления хранится в настройках папки. Предлагаемые единицы — секунды,
  `0` отключает периодические вызовы, но не ручной Refresh. Предлагаемый default
  для Codex — 60 секунд; для PM2 сохранить текущую частоту около 2 секунд.
- Обновлять при старте сервиса, вручную и после успешного изменения источника.
  Не запускать одновременно несколько операций одного источника; не накапливать
  очередь таймерных вызовов, если предыдущий ещё работает.
- Предложение: ручной Refresh также перечитывает изменённый JS без рестарта сервиса.
- Refresh создаёт только idle-слоты, не запускает команды. Запрет автозапуска
  сохранённых/импортированных консолей при старте сервиса сохраняется.
- Порядок задаёт источник. Повторный refresh не создаёт дубли и процессы.
- Для работающих консолей действуют Q07–Q08: внешний пропуск не убивает процесс,
  новые команда/cwd ждут явного Start/Restart. Предложение: при возвращении
  того же ключа в источник снять `orphaned` без создания дубликата.
- Ошибка чтения не равна пустому списку: сохранить последний успешный состав
  и процессы, показать ошибку папки. Успешный пустой список обрабатывать отдельно.
- Ошибки CRUD показывать внизу открытой формы. Для ошибки update вернуть исходные
  значения; не закрывать диалог и не менять локальную запись до успеха обработчика.
- Явный Delete требует подтверждения. Только после успешной записи источника
  останавливать удаляемую сессию и убирать слот. При неуспехе сохранить его.
- Ошибку «запись успешна, следующий refresh не удался» показывать отдельно:
  произвольный JS не даёт общей транзакции или гарантированного отката.
- Скрипт сохраняет посторонние разделы, обнаруживает конфликты внешних изменений
  и не переформатирует весь Markdown. Маркер `DELETED` добавляется однократно;
  помеченные разделы не возвращаются из refresh.
- Изменение внешнего потребителя этого Markdown, например WezTerm, пока не входит
  в согласованный объём: его парсер сам по себе не начнёт учитывать новый маркер.

### 4.5. PM2 как scripted-источник

Простого массива команд недостаточно: PM2 показывает уже существующие чужие
процессы. Нельзя вместо мониторинга запустить дубли их команд через yconhost.

Предложение: общий контракт поддерживает внешние readonly-элементы. Их источник
возвращает внешний ключ и статус, а отдельная необязательная точка входа, например
`readOutput(context, item, options)`, читает хвост вывода. Схему состояния/вывода
проверяет сервер; необязательные возможности описываются общим контрактом.
Названия PM2, `pm2 jlist` и чтение его логов находятся в отдельном JS, не в ядре.

Предлагается сохранить текущий read-only объём PM2: без create/update/delete,
ввода и управления процессами. Требуется подтверждение F03. Не добавлять новые
операции управления PM2 только из-за изменения типа папки.

### 4.6. UI, HTTP, MCP и выполнение JS

- В каждой папке есть Settings; у источников — Refresh. Верхнего Codex-импорта
  больше нет. Старый import API/MCP удаляется без alias.
- Возможности Create/Edit/Delete определяются обработчиками источника. Отсутствие
  обработчика не подменяется локальной мутацией, пропадающей при refresh.
- Обычный rename заголовка тоже проходит через `update`, не обходит источник.
- Создание и изменение используют общую форму `defineFields`; ошибка видна
  под полями. Отмена/закрытие формы не меняет источник.
- UI, HTTP и MCP используют один путь операций и одинаковые проверки. У HTTP/MCP
  ошибка возвращается структурированно; сброс полей относится к состоянию UI.
- Сохраняются поиск, компактный режим, Touch mode, цвета, карточки, Gather errors,
  существующие правила manual/mywins и временных ручных сессий.
- Предложение: выполнение JS отделить от основного серверного потока и ограничить
  по времени, чтобы зависание не блокировало UI и терминалы. Это защита доступности,
  а не безопасная песочница. Не загружать исполняемый код из браузера или URL.

## 5. Последние уточнения

### F01. Как понимать Q02

Правильно ли считать оба ответа отрицательными: скрипт не описывает поля Settings,
а тип существующей папки в первой версии нельзя менять через Settings?
Однократная миграция codexes/PM2 при обновлении — отдельная процедура, не такая смена.

### F02. Поля формы Codex

Какой набор должен возвращать `defineFields` именно этого скрипта? Предложение:
`name`, `description`, `session_id`, `cwd`. Нужны ли также редактируемые команда
и цвет, или их оставляем результатом логики скрипта/источника?

### F03. Объём PM2

При переносе в scripted сохраняем нынешний readonly-мониторинг без запуска,
остановки, удаления и редактирования процессов? Предложение: да; внешнее состояние
и чтение логов доступны через общий контракт, специальных PM2-веток в ядре нет.

   Только после этого начинается реализация.

   Ввести контракт JS, запуск refresh по настройке и обработку ошибок.
3. Вынести Codex/Claude и PM2 в собственные JS-файлы; убрать специальный импорт

   если подтверждён F03, без запуска дублирующих процессов.
4. Мигрировать папки/ID без потери логов, Gather errors, прочтения и времени запуска.
   Миграция не запускает команды и не добавляет UUID во внешние источники.
5. Реализовать Settings, общий Refresh, формы defineFields и CRUD источников;

6. Сначала проверить на копиях Markdown/mywins и отдельном сервере. До широких

   Применение к живому сервису и исходным файлам согласовать отдельно.

## 7. Критерии приёмки для согласования

- Две scripted-папки с собственными JS работают независимо; имя папки не включает
  специальную бизнес-логику ядра. Codexes и PM2 пользуются общим механизмом.
- Default/manual и оба имени файлов mywins сохраняют согласованное поведение.
- Нет верхнего Import Codex contexts и старого API/MCP; есть Settings и Refresh.
- Период обновления сохраняется в Settings. Таймер не создаёт параллельные refresh.
